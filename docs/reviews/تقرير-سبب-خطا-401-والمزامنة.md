# مراجعة — لقيت سبب خطأ 401 وأخطاء تانية جديدة

لاحظت إن المشروع اتغيّر بشكل كبير من المرة اللي فاتت — بقى فيه نظام مزامنة احترافي
جديد (`/api/sync/pull` و `/api/sync/push`) بيشتغل بالـ cursor (يجيب بس اللي اتغيّر من
آخر مزامنة) بدل ما يسحب كل حاجة من الصفر في كل مرة. ده تحسين كبير، وراجعته بالكامل.

## سبب خطأ 401 (Unauthorized) — لقيته 🔴

```
GET /api/sync/pull?... 401 (Unauthorized)
```

نظام المزامنة الجديد بيطلب توكن حقيقي (JWT موقّع) في الـ header عشان يتأكد إنك فعلاً
مسجل دخول. المشكلة إن تسجيل الدخول في وضع الديسكتوب (`handleLogin` في
`desktop-api.ts`) كان بيرجّع التوكن ده:

```js
return { token: user.id, ... }   // ❌ ده مجرد الـ id بتاع المستخدم، مش توكن حقيقي!
```

يعني التوكن اللي البرنامج كان بيبعته للسيرفر مع كل طلب مزامنة **مش توكن موقّع أصلًا**
— هو بس رقم الـ id بتاع المستخدم. والسيرفر (`verifyToken`) بيتأكد إن التوكن ده حقيقي
وموقّع بمفتاح السيرفر السري — وطبعًا `user.id` مش موقّع بحاجة، فبيرفضه فورًا برسالة
401. يعني تسجيل الدخول المحلي كان شغال تمام (بيتأكد من كلمة المرور صح جوه SQLite)،
بس التوكن الناتج مالوش أي قيمة عند السيرفر الحقيقي — فأي مزامنة كانت **مستحيلة** من
الأساس، بغض النظر عن أي حاجة تانية.

## الحل
خليت البرنامج، لما يعمل تسجيل دخول محلي ناجح **وكان فيه نت وقتها**، يعمل كمان تسجيل
دخول حقيقي على السيرفر (`/api/auth/login`) بنفس اليوزر والباسورد، وياخد منه التوكن
**الحقيقي** الموقّع، ويستخدم ده في كل طلبات المزامنة بدل الـ id. لو مفيش نت وقت
تسجيل الدخول، البرنامج يفضل شغال عادي تمامًا محليًا (زي ما هو)، والمزامنة بس بتفضل
واقفة لحد ما تسجل دخول تاني والنت يكون شغال.

**ملاحظة مهمة**: عشان الحل ده يشتغل، لازم يكون فيه نت وقت **تسجيل الدخول نفسه** (مش
أي وقت بعد كده). يعني الأفضل إنك تسجل دخول والنت شغال في بداية الشيفت، وبعد كده
البرنامج يقدر يشتغل أوفلاين طول اليوم وهو لسه محتفظ بتوكن مزامنة صالح.

## أخطاء تانية لقيتها من اللوج اللي فات وصلحتها

### 1. حفظ الإعدادات (`PUT /settings`) — خطأ "near WHERE: syntax error"
جدول الإعدادات شكله مختلف عن باقي الجداول (بيتخزن كـ `key/value/category` مش صف واحد
بـ `id`)، لكن الكود كان بيعامله زي أي جدول عادي، فكانت بتتبعت جملة SQL ناقصة تمامًا
(`UPDATE settings SET  WHERE id = ?` من غير أي عمود!). بنيت له معالج خاص بيحدّث كل
إعداد على حدة صح.

### 2. إضافة موظف جديد — "NOT NULL constraint failed: users.password_hash"
شاشة إضافة الموظفين كانت بتبعت كلمة مرور **من غير تشفير**، لكن الكود كان بيتعامل
معاها زي أي حقل عادي فمكنش بيحوّلها لـ `password_hash` (العمود المطلوب فعليًا) —
فكانت بتضيع تمامًا وتفشل الإضافة. بنيت معالج مخصوص لإضافة الموظفين بيشفّر كلمة المرور
صح (bcrypt) قبل الحفظ، وخليت البريد الإلكتروني حقل إجباري في النموذج (كان اختياري
بالغلط، مع إنه مطلوب وفريد في قاعدة البيانات — نفس مشكلة الباركود والتليفون اللي
صلحناها قبل كده، بس هنا كان أخطر لأنه NOT NULL مش بس UNIQUE).

## الخطوات
1. استبدل `src/lib/desktop-api.ts` و `src/components/modules/employees.tsx` بالنسخ
   المرفقة.
2. Push للـ GitHub وتأكد إن Vercel عمل Deploy جديد.
3. بيلد جديد للديسكتوب: `cd src-tauri && cargo clean && cd .. && npm run tauri:build`
4. **مهم جدًا**: سجّل خروج ثم سجّل دخول تاني **والنت شغال** — تسجيل الدخول القديم
   لسه معاه التوكن الغلط المخزّن، ولازم تسجّل دخول جديد عشان تاخد التوكن الصحيح.
5. تابع الـ Console — المفروض متشوفش 401 تاني، والمزامنة تشتغل عادي.

لو ظهر أي خطأ تاني بعد كده، ابعتلي الـ Console زي ما بنعمل دايمًا.
